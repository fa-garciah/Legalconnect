# Contracts: Authentication & Multi-Factor Enrollment

**Feature**: `003-authentication-mfa` | **Date**: 2026-09-09

REST over JSON, continuing `001`'s conventions exactly — see
[001/contracts/README.md](../../001-tenant-foundation/contracts/README.md) for media type,
identifiers, timestamps and the error body shape, all unchanged.

Three surfaces, all new, all **pre-authentication by definition**:

| Contract | Surface | Consumer |
|---|---|---|
| [authentication.md](./authentication.md) | Public — no identity resolved yet | Anyone attempting to sign in |
| [enrollment.md](./enrollment.md) | Pending-enrollment — an identity with no confirmed factor | A person who accepted an invitation and must enroll |
| [recovery.md](./recovery.md) | Pending-challenge — a sign-in past the credential step | A person who lost their authenticator |

---

## These routes are ungated, and that is correct

**`004`'s authorization interceptor does not and must not gate any route in this
directory** (FR-040). Every one of them is reached before an authenticated,
membership-resolved principal exists — that is what they exist to produce. There is no
archetype to check a capability against, no tenant to scope to, and no entitlement to
consult.

This is stated positively, in the contracts and in `spec.md`, so that a future reviewer or
audit does not file an ungated authentication route as a missing-authorization defect. The
gate these routes are subject to is **state**, not capability:

| Route class | Reachable only when |
|---|---|
| Credential step | Always — it is the entry point |
| Challenge step | A credential step for this attempt has succeeded |
| Enrollment | The identity has no confirmed factor |
| Recovery re-enrollment | A recovery challenge was just satisfied |

None is a general-purpose surface. Presenting a challenge answer with no pending
challenge, or beginning enrollment for an already-enrolled identity, is refused.

---

## This is the slice that brings `002`'s surfaces onto the network

`002/contracts/README.md` states that none of its surfaces may be network-exposed before
this slice lands, and lists four test-only headers standing in for real verification:
`x-identity-id`, `x-tenant-id`, `x-subject`, `x-email`.

On delivery of this slice
([research D10](../research.md#d10--002s-routes-come-onto-the-network-by-replacing-the-header-stand-ins-with-the-session-guard)):

| Header | Fate |
|---|---|
| `x-identity-id` | **Removed** from every network-reachable path. The identity comes from the session |
| `x-subject` | **Removed.** The subject is generated by the product at acceptance, never supplied |
| `x-email` | **Removed.** The authenticated email comes from the resolved identity |
| `x-tenant-id` | **Kept.** It was never a claim of identity — it names which tenant to activate, and `002/FR-016` already requires that to be membership-verified rather than trusted |

All four remain available in tests, behind the same test-only boundary. SC-030 asserts the
three identity headers are accepted on zero network-reachable surfaces.

The asymmetry is deliberate: removing `x-tenant-id` too would break `002/FR-013`, because
naming the active tenant is the caller's job and always was. What must not be trusted is
*who the caller is*.

## The uniform refusal rule

Every failure across these three contracts answers with the **same generic body and
status**, with one deliberate exception. A caller must not be able to distinguish:

- an email with no identity from a wrong credential (FR-004, SC-017);
- a wrong TOTP code from an invalid, consumed or nonexistent backup code (FR-022, FR-030,
  SC-016);
- a locked account from a wrong code (FR-055);
- an unavailable encryption key from a wrong code (FR-017, SC-009).

```json
{ "error": "authentication_failed", "message": "No fue posible completar el acceso." }
```

`401 Unauthorized`. No field distinguishes cause, and no timing difference should either —
which is why backup-code verification performs a fixed number of comparisons
([research D11](../research.md#d11--backup-code-verification-tries-every-unconsumed-code-with-no-early-exit-timing-signal)).

**The one exception** is `mfa_enrollment_required`, which `002` already ships and `004`
already fixed as position 1 of its refusal ordering. It answers `403` and names its
remedy, because the caller has already proved who they are and telling them to finish
enrolling discloses nothing they do not already know. `002`'s plan justified this same
departure for the same reason.

## What is *not* here

- **Sign-out, session listing, session revocation and step-up.** All `005`. This slice
  emits a session (FR-033 to FR-038) and stops.
- **Standalone backup-code re-issuance.** Withheld from production until `005` supplies
  step-up (FR-032). Re-issuance *inside* the recovery flow is in
  [recovery.md](./recovery.md) and ships now.
- **Assisted MFA reset.** `US14`–`US17`, IT2. No route exists, and no archetype holds the
  capability — see `spec.md` Named Risks for the gap this leaves.
- **Password change or reset.** No story in this slice's set covers it.
- **Any route returning a factor secret or a backup code.** By construction. `lc_app` holds
  no grant that could read either
  ([research D3](../research.md#d3--authentication-material-lives-in-tables-lc_app-cannot-reach-verified-inside-security-definer-functions)).
