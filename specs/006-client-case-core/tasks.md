## Dependencies & Execution Order

### Phase Dependencies

```
Phase 1 Setup (T001 is a hard gate)
   └─> Phase 2 Foundational (T006–T031) ── BLOCKS EVERYTHING
          ├─> Phase 3 US1 Client (T032–T037)
          │        └─> Phase 4 US2 Case (T038–T044)   [needs a client to open against]
          │                 └─> Phase 5 US3 Team (T045–T054)  [needs a case to staff]
          └─────────────────────────> Phase 6 Polish (T055–T064)
```

The user stories are **not** independent of each other here, and pretending otherwise
would be dishonest: a case needs a client, and a team needs a case. That is the nature of
a domain root. What each story *is* is independently **testable and demonstrable** at its
own checkpoint, which is the property that matters for incremental delivery.

### The one cross-module task

**T052b modifies a 002 file.** It is the only task outside Phase 2 that touches another
slice's code, and it is easy to lose in a large diff — call it out in the PR description
next to T018's `interceptor.ts` change, since those two are the whole of this slice's reach
into 002 and 004.

### Within Phase 2, the critical path

`T006 → T008 → T010 → T011` (schema) and `T016 → T017 → T018 → T019` (the `targetId`
seam) are two strict chains. **T016–T019 is the one that gates everything else** — until
`targetId` is populated, no `assigned` route works for anyone, and T020–T023's resolver
has nothing feeding it.

### Parallel Opportunities

- **T004, T005** — Setup, independent
- **T006, T007, T009** — three migration files, no overlap
- **T014, T015** — actions and errors, different files
- **T020, T024, T025, T029** — four independent test files in Foundational
- **T032, T032a, T032b, T033** — US1's four test files
- **T038, T039, T040, T040a** — US2's four test files
- **T045, T046, T047, T048a, T049** — US3's five test files (T048 extends T047's file, so it is *not* parallel with it)
- **T055, T055a, T056, T057, T060, T063** — Polish, mostly independent
- **T025 and T025a** share a file, so they are sequential despite both being marked `[P]` relative to other tasks

### Two-person strategy

Phase 2 is where staffing helps most and is easy to split: one person takes the schema
chain (T006–T011) and the catalogs (T024–T030), the other takes the registries (T012–T015)
and the `targetId`/resolver chain (T016–T023). They converge at T031.

Phases 3–5 are a strict sequence. A second person is better used writing Phase 5's four
test files (T045–T049) while the first implements Phase 4, since those tests describe
behaviour the design already fixes and need no code to be written against.

## Implementation Strategy

### MVP (User Story 1 only)

1. Phase 1 Setup — T001–T005, with **T001 merged first**
2. Phase 2 Foundational — T006–T031 (blocks everything)
3. Phase 3 US1 — T032–T037
4. **STOP and VALIDATE**: a firm can register, correct and withdraw the parties it
   represents, tenant-isolated and audited

Phase 2 is heavy for an MVP that only delivers clients. That is unavoidable: the schema,
the registries and the `targetId` seam are shared by all three stories, and splitting them
per story would mean three migrations touching the same tables.

### Incremental Delivery

1. Setup + Foundational → six tables, eleven capabilities, a working resolver, three
   seeded catalogs
2. **US1** → the client register **(MVP)**
3. **US2** → matters can be opened, readable by `MP`/`SA`
4. **US3** → case teams, and `assigned` scope becomes real for every archetype
5. Polish → grant audit, the inherited-suite guarantee, 016a's unblocking

### What to demo at each checkpoint

- After US1: register a client with no RFC, correct it, withdraw it, show tenant B sees
  nothing
- After US2: open a consultative matter with no venue, show the court's number in its own
  field beside the firm's
- After US3: two people on a matter, remove one, and show their **very next** request
  refused — identically to a matter that does not exist
